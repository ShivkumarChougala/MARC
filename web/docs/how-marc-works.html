How MARC works

What happens on your Mac when you connect from your iPhone.

The short version

MARC connects your iPhone to your Mac over SSH. Your Mac collects the readings, runs commands, and handles file actions. MARC sends requests through the encrypted connection and turns the replies into screens and graphs.

  1. You connect to your Mac’s Remote Login service using a Mac account.
  2. MARC checks the Mac’s SSH host identity, then authenticates your account.
  3. A monitoring collector starts automatically. Other readers run when their views need them; changes such as uploading a file or stopping a process require an action from you.
  4. Readings return to iPhone. Monitoring history is also saved under your Mac account; previews and downloads create temporary iPhone copies.

Your Mac must be awake and reachable from your iPhone. MARC connects directly, with no built-in internet relay. For access away from home, you need a secure route such as a VPN you configure separately. Start with Connect your Mac.

Identity, login, and data flow

Before signing in to a new Mac, MARC reads its public SSH host key and asks you to compare the key type and SHA256 fingerprint with that Mac. It remembers your approval for the host and port. An unexpected key change blocks later connections. Approval alone does not prove you reached the intended Mac.

Password login sends your username and password inside SSH. Key login uses an imported OpenSSH Ed25519 private key to sign on iPhone, without uploading the private key or passphrase. Your Mac must already authorize the matching public key. See SSH keys and Security & privacy.

After login, MARC checks that the server runs macOS. It sends embedded scripts to python3 through SSH. Monitoring and process collectors return one JSON object per line; other helpers return a JSON result. MARC reads these replies to update the display. Terminal output and SFTP transfers use separate formats.

Which features share a connection?

One SSH connection can carry several channels. A new command channel does not necessarily open another network connection.

What runs on your Mac

Monitoring starts automatically. A Python collector reads CPU, memory, storage, network, and available power information. It also tries to save history, even when Statistics is closed.

Process readers run when needed. Status’s top-process preview and the Processes view read a stream based on ps. Each stream uses a temporary stop marker. The reader can appear in its own process list.

Helpers handle individual requests. Browsing files, reading history, and refreshing controls or services run short requests. Uploading, editing, deleting, stopping processes, or changing controls requires your action.

Terminal opens a Mac shell. Your shell’s startup files and the programs you run determine what else starts. Files uses the Mac’s SFTP subsystem.

Python 3 must be installed and available as python3 to the SSH account. MARC supplies its scripts with each request; its collectors need no extra Python packages. Connecting does not install Python, a persistent MARC helper, a LaunchAgent, a LaunchDaemon, a scheduled job, or an executable collector script.

MARC does write history, stop markers, and temporary transfer files. Commands you run, optional tool installation, and service actions can make lasting changes. See Control Center and Services & Docker for prerequisites.

How to read the numbers

CPU: total and per-core activity come from changes in macOS CPU ticks, excluding idle ticks. User CPU includes user and nice ticks; system CPU is separate. These are whole-Mac readings, including other apps and macOS—not a measurement of MARC’s overhead.

Processes: CPU compares accumulated process CPU time with elapsed time. One busy core is about 100%, so a process can exceed 100%. Process memory is resident size (RSS). These figures do not add up directly to the whole-Mac display.

Memory: MARC subtracts free, inactive, and speculative pages from physical RAM using vm_stat’s page size. The estimate includes active, wired, and compressed resident usage; swap is separate. When macOS reports file-backed pages, MARC uses them to estimate cached files. MARC does not report a separate compressed-memory amount or reproduce Activity Monitor’s categories exactly.

Storage: capacity comes from the APFS Data volume. Displayed used space is total minus available, including shared-volume usage; it is not a folder-size total. Disk activity comes from storage-driver byte counters and is not limited to that volume.

Network and disk activity: MARC subtracts successive byte counters and divides by elapsed time. Network readings cover the default-route interface. Missing counters, a reset, or an interface change can leave rates unavailable until a valid pair arrives. These readings are not internet speed tests.

Sampling, slower readings, and gaps

The monitoring loop sleeps one second between collections, plus the time needed to run commands. The 1, 2, or 5 second refresh setting controls display updates; it does not change that sleep or every helper’s interval.

Storage capacity, process count, swap, and local IP refresh about every five seconds. Battery charge and power source use the selected 5, 10, 30, or 60 second interval (10 by default), applied when reconnecting. Battery health is read in a separate thread at most about once a minute when a battery is detected. Processes target one-second cycles; Control Center waits five seconds between refreshes, with wireless reads roughly every 30 seconds. Services & Docker readers use an eight-second refresh cadence. Request duration and failures can lengthen all these intervals.

Missing data does not mean zero usage. Some optional values become unavailable; slower readings can retain an earlier value after failure. A failed capacity read currently returns zero placeholders, not a real zero-capacity disk. Check connection status, update feedback, and permissions.

Invalid collector output can leave the last readings visible with a delay message. Repeated errors or about 90 seconds without a valid sample end the monitoring connection and allow reconnection when eligible. This does not check the freshness of every optional field.

The iPhone’s live chart buffer keeps about five minutes, capped at 300 points. Saved-history views request 15, 30, or 60 minutes and average samples into five- or ten-second buckets. Archived rates are not calculated across gaps over 120 seconds. Disconnections, backgrounding, failed writes, and clock changes can affect the record; charts do not imply continuous recording or reconstruct missing activity.

For the screens and common interpretation questions, see Monitoring and Processes.

What Activity Monitor may show

Activity Monitor may show SSH sessions, Python collectors, short-lived commands such as ps, vm_stat and ioreg, an SFTP server, and your Terminal programs. Names vary with macOS and your installation: examples include sshd, sshd-session, Python, python3, sftp-server, and zsh.

MARC does not hide its collectors from the process list. A reader or its subprocess can appear there too. Check its account, identity, and timing; a process name alone does not identify it as MARC’s.

Storage, retention, and cleanup

The collector tries to save monitoring JSON about every five seconds in ~/.local/share/marc/history.sqlite. The marc_samples_v1 table stores a timestamp and payload under the SSH account. New history files and directories use private permissions; existing directory permissions are not automatically repaired.

Samples contain CPU and per-core activity, memory, storage, network/disk counters, interface and time. They also include hostname, username, local IP, hardware/OS details, core/process counts, uptime, load, swap, and available power/health readings. They do not include process lists, Terminal transcripts, file contents, control/service results, or AI prompts.

On its first successful save, then about once a minute while active, the collector removes its own rows older than two hours. Deletion is not scheduled after disconnect. Legacy samples rows remain readable. Failed writes retry later without stopping valid live readings.

Removing a profile or uninstalling MARC does not delete history on the Mac. Stop MARC sessions using that account before removing the database separately. Deletion does not securely erase disk pages, backups, or administrator logs.

Temporary files and iPhone storage
  • Process streams: ~/.local/share/marc/process-stream-<UUID> is an empty stop marker, not an executable. The loop checks its existence. On cancellation MARC attempts to unlink it using another SSH command; the reader also removes it on normal exit. A broken connection or abrupt termination can leave a marker. Removing an abandoned marker stops a reader only if it is still running and checking that marker.
  • Uploads and edits: Mac destination folders can contain .marc-upload-<UUID>.part and .marc-edit-input-<UUID>.part staging files. Text replacement can also create a .marc-edit- temporary file. Helpers attempt private staging permissions and cleanup. An interrupted operation can leave content behind; check its outcome before deleting leftovers or retrying.
  • Folder archives: Python creates a marc-folder- directory under the Mac account’s temporary directory, containing a .tar.gz. MARC attempts cleanup after transfer or preparation failure. If the app cannot receive the archive path or contact the Mac again, removal may not complete. No MARC scheduled sweeper is installed on the Mac.
  • iPhone copies: previews, downloads and app-imported uploads use MARC-owned temporary storage with iOS Complete Protection and backup exclusion. Cleanup is attempted when the last transfer/preview/share owner releases its copy, and at startup for recognized abandoned folders. Failures or system interruption can leave copies until later cleanup or system removal. Exported Files or other-app copies are independent; MARC does not delete them.
  • Other local state: profiles/preferences use app storage; saved passwords, SSH keys/passphrases, API keys and trusted host identities use device-only, unlocked-device Keychain access. Current readings, process/service results, and Terminal display buffers are held in app memory. Shells and services can keep their own logs/history on the Mac. Profile removal is separate from removing reusable keys and fingerprints; uninstalling does not reliably clear Keychain.

See Files, Security & privacy, and the Privacy Policy for storage choices and limits. Only remove files you have identified as abandoned and no longer need.

Permissions and connection lifecycle

Every operation uses the connected Mac account’s permissions. macOS privacy protections, desktop-session requirements, and installed tools’ access still apply. SSH does not bypass these restrictions or create a separate MARC sandbox.

Monitoring and list queries read data, but monitoring also writes history and process readers create stop markers. File changes, termination, controls, app launches, and service actions change the Mac. Stopping a process can lose unsaved work, and a manager may restart it. Disconnecting does not undo completed actions.

When MARC enters the background, it cancels monitoring, pauses Terminal sessions, stops Files work, and attempts to close their connections. Readers tied to a view are canceled when no longer needed. Foreground reconnection starts new work; it does not fill recording gaps. Terminal text can remain in memory after the remote session ends.

Cancellation and remote process exit do not happen at the same instant. The monitoring collector exits when its output raises a broken-pipe error; process readers also use stop markers. Network loss, a blocked command, or delayed SSH teardown can delay cleanup.

Your programs may stop or continue after disconnection, depending on their configuration. MARC does not guarantee persistent Terminal jobs or automatically stop services and containers you started. Check the outcome before retrying an interrupted action.

What can leave your devices?

Monitoring, Files, Terminal and control replies travel directly over SSH between your devices, with no MARC-operated relay. Discovery and hostname lookup also use local or network naming services.

AI starts Off and is available only for Terminal command suggestions. Local mode sends your prompt, model and instructions over SSH to Ollama on the Mac’s loopback address. Its configuration determines further logs and network activity. API mode sends them from iPhone to your chosen OpenAI, Google Gemini, Groq, or custom HTTPS endpoint, including the selected API key and normal request metadata such as your public IP.

The first API prompt to an endpoint in a Terminal session needs approval. Later prompts still require your action; connection or relevant settings changes reset approval. Loading a provider’s model list asks separately and sends no prompt. Terminal output, files and Mac credentials are not attached automatically, but anything pasted into your prompt is sent. Review suggestions at an empty shell prompt before choosing Run.

Commands you run, tool installation, launched apps, and services or containers can make their own network connections. File providers may fetch cloud content; sharing destinations receive the copies you send. See Local & API AI and the Privacy Policy for recipients, consent and retention.

Why use this approach?

SSH uses macOS Remote Login and your existing account over an encrypted connection. macOS tools provide the readings without a separately installed MARC monitoring agent. The source is open for inspection.

Python must be available, your Mac must stay reachable, and permissions and hardware support vary. Collectors, commands, history writes, encryption and transfers use resources. AI models and programs you start add their own load. MARC does not claim zero overhead or a measured performance figure.

For connection or collection problems, see Troubleshooting.
